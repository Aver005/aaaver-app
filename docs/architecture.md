# Архитектура

Проект состоит из двух частей, живущих в одном репозитории:

- `src/` — React SPA, собирается vite'ом в `dist/`;
- `server/` — сервер на Bun: раздаёт `dist/`, держит API и ходит в Postgres.

В проде работает один процесс (`bun server/index.ts`), в деве два:
vite dev-сервер на :5173 проксирует `/api` на bun-сервер на :3001
(`bun dev` = `bun run --parallel dev:web dev:api` — оба поднимает сам Bun,
вывод помечен именем скрипта).

## Фронтенд: FSD

Классические слои Feature-Sliced Design, импорты только сверху вниз:

```
app/        точка входа, роутер, провайдеры, глобальные стили
pages/      home — композиция виджетов
            admin — панель управления, отдельным ленивым чанком
widgets/    navbar, hero, about, experience, projects, open-source,
            stack, contact, footer
features/   contact-form (форма + slide-to-send + pow),
            locale-switch (RU/EN)
entities/   project, experience, skill, repo — типы, данные, карточки
shared/     ui-кит, i18n, api-клиент, pow-солвер, конфиг
```

Правило простое: виджет может импортировать фичи/сущности/shared,
фича — сущности/shared, сущность — только shared. Внутри слайса наружу
торчит только `index.ts`.

### Контент

Весь контент — статика в коде, БД для него не нужна:

- тексты интерфейса: `shared/i18n/dict.ts` (словарь RU/EN);
- проекты, опыт, стек: `entities/*/model/data.ts` с двуязычными полями.

Исключение — секция Open Source: она тянет живые данные с GitHub через
серверный кэш (`/api/github/repos`), а на время загрузки/при ошибке
показывает снимок из `entities/repo/model/fallback.ts`.

### Локализация

Без библиотек: словарь + React-контекст (`shared/i18n`). Язык берётся
из адреса: `/` — русская версия, `/en/` — английская
(`shared/config/seo.ts`). Ни `navigator.language`, ни localStorage:
у пререндера их нет, и первый рендер в браузере разошёлся бы с HTML.
Переключатель — обычная ссылка на другую версию. Контентные строки
в entities хранятся как `{ ru, en }`, достаются хелпером `lx()`.

### Пререндер и SEO

`bun run build` = `vite build` → `vite build --ssr src/app/entry-server.tsx`
→ `scripts/prerender.ts`. Скрипт рендерит `App` в `StaticRouter` для
каждого языка и пишет в `dist/`:

- `index.html`, `en/index.html` — весь текст страницы, свой `<html lang>`,
  title, description, canonical, hreflang, og и JSON-LD (Person, WebSite,
  ProfilePage);
- `shell.html` — пустая оболочка с noindex для админки и 404;
- `sitemap.xml` (портфолио; корни демок сервер дописывает на лету) и `llms.txt`.

`main.tsx` гидрирует разметку, только если `#root[data-route]` совпадает
с адресом; иначе рендерит с нуля. При смене языка head догоняет
`useDocumentHead` в `App.tsx`.

Что обязана соблюдать любая правка фронтенда:

- в рендере никаких `window`, `document`, `localStorage`, `navigator`,
  `Date.now()`, `Math.random()` — только в эффектах и обработчиках;
  данные с API стартуют со статичного значения, которое одинаково
  на сервере и в браузере;
- новый язык или новая индексируемая страница — запись в `PAGES`
  (`shared/config/seo.ts`), папка в `RESERVED` у демок и проверка
  `seo-crawl-audit` после сборки;
- неизвестные пути отвечают 404, не надо возвращать SPA-фолбэк.

## Сервер

Чистый `Bun.serve` с маршрутами, ни одной npm-зависимости — обновлять
и чинить нечего, рантайм-уязвимостям взяться неоткуда. Клиент Postgres
тоже встроенный (`Bun.SQL`), так что и база зависимости не приносит.

```
server/
  index.ts        Bun.serve: роуты + статика + фоновые задачи
  config.ts       все env-переменные в одном месте
  db/
    client.ts     подключение Bun.SQL, различение «база лежит» и «наш баг»
    migrate.ts    раннер миграций под advisory-блокировкой
    migrations/   *.sql по порядку имён
    index.ts      фасад: готовность, settings, чистка протухшего
  lib/
    pow.ts        проверка proof-of-work
    rate-limit.ts лимиты по IP (таблица attempts)
    telegram.ts   отправка в TG + автопоиск chat_id
    http.ts       json-хелпер, определение IP клиента
    static/       конвейер статики (см. ниже)
      index.ts    порядок обработчиков: sitemap → сайты-демки → портфолио
      types.ts    контракт StaticHandler
      files.ts    безопасный join, кэш-заголовки, отдача файла
      sites.ts    демки из sites/ на роутах /<slug>/
      sitemap.ts  sitemap.xml из сборки + корни смонтированных демок
      app.ts      dist/ портфолио: пререндер, оболочка, честный 404
    jwt.ts        проверка HS256 на crypto.subtle (токены панели)
    cookie.ts     разбор Cookie и сборка Set-Cookie
  routes/
    challenge.ts  POST /api/challenge
    contact.ts    POST /api/contact + фоновый ретрай недоставленного
    github.ts     GET /api/github/repos с кэшем в базе
    sites.ts      GET /api/sites — список смонтированных демок
    admin/        панель: вход через SSO, сессии, чтение состояния демок
```

### Роутинг фронтенда

Роутер один и нужен ровно для одного: развести портфолио и панель
управления. Всё, что не `/admin`, — портфолио (звёздочкой, а не только
`/`: по битой ссылке человек видит главную, хотя сервер и отвечает 404).
Язык портфолио определяется тем же адресом, маршрут у обоих языков один,
чтобы переключение не пересоздавало страницу.

Админка подгружается `lazy` отдельным чанком. Это не преждевременная
оптимизация, а единственная причина, по которой роутер здесь уместен:
портфолио — маркетинговая страница, её бандл не должен таскать с собой
интерфейс, который видит один человек.

### Админка

Подробно — в [admin.md](admin.md). Коротко: вход через панель
`root.kiviuly.ru` по implicit-потоку (обмена кода на токен быть не может
— панель слушает `127.0.0.1` и unix-сокет, из контейнера до неё не
дотянуться), утверждение приезжает POST-ом формы, проверяется подпись,
`iss`, `aud`, `exp`, `state` и одноразовость `jti`, дальше заводится своя
сессия на 12 часов.

Две вещи, которые ломаются молча и потому вынесены сюда:

- временная cookie со `state` обязана быть `SameSite=None; Secure` —
  возврат приходит кросс-сайтовым POST-ом, и при `Lax` браузер её просто
  не пришлёт;
- слаг `admin` забронирован в `RESERVED`: обработчик демок пробуется
  первым, и папка `sites/admin/` иначе перекрыла бы панель.

### Статика: конвейер обработчиков

Всё, что не `/api/*`, проходит через `lib/static/index.ts` — список
обработчиков, которые пробуются по порядку; каждый либо отдаёт Response,
либо возвращает `null` («не моё»). Сейчас их три:

1. `sitemap.ts` — `/sitemap.xml`: файл из сборки плюс `/<slug>/` каждой
   смонтированной демки (`lastmod` из `.release.json`). Демки появляются
   без пересборки, поэтому список собирается на лету. Демка, чей
   canonical смотрит на другой хост, в sitemap не попадает.
2. `sites.ts` — демки. Папка `sites/<slug>/` с чужим собранным `dist`
   (внутри обязан быть `index.html`) раздаётся как самостоятельное SPA
   на `/<slug>/`. `/slug` редиректится на `/slug/` (308), неизвестные
   пути без расширения падают на `index.html` демки — её клиентский
   роутинг работает. Слаг — только `[a-z0-9-]`, имена `api`, `assets`,
   `projects`, `admin`, `en` зарезервированы за портфолио.
3. `app.ts` — сам портфолио из `dist/`; всегда последний. `/` и `/en/` —
   пререндеренные страницы, `/en` и `…/index.html` — редирект 308 на адрес
   со слэшем, `/admin` — `shell.html` с `X-Robots-Tag: noindex`, любой
   другой путь без расширения — та же оболочка со статусом 404.

Новая статичная фича (файлы по маске, ещё один каталог, отдельная
страница) — это новый обработчик в списке, существующие не трогаются.

Наполняется `sites/` двумя путями: руками (`deploy-site.bat`) или
автоматически — `scripts/sites-updater.ts`, отдельный процесс, который
опрашивает релизы GitHub/GitLab по реестру, скачивает `dist.tar.gz` и
атомарно подменяет папку демки. Внутри каждой развёрнутой демки лежит
метка `.release.json` с версией — по ней апдейтер понимает, что обновлять
(дотфайлы демок сервер наружу не отдаёт).

### Реестр демок

Таблица `sites` в базе: слаг, провайдер, `owner/repo`, ассет, тег,
выключатель. Раньше это был `sites.config.json` в репозитории — файл
убран, потому что панель не может править то, что перезаписывается при
`git pull` и при каждой пересборке образа.

Права на два хранилища разведены и не пересекаются:

|            | Реестр (база) | Диск (`sites/`) |
| ---------- | ------------- | --------------- |
| сервер     | пишет         | только читает   |
| апдейтер   | только читает | пишет           |

Поэтому договариваться двум процессам не о чем, и блокировок между ними
нет. Апдейтер не применяет миграции — их владелец сервер; недоступный
реестр для апдейтера означает пропущенный цикл, а не падение.

Реестр — это НАМЕРЕНИЕ, диск — ФАКТ, и панель показывает оба. Расходятся
они законно: сайт добавили, а апдейтер ещё не сходил (`ждёт`); демку
залили руками мимо реестра или убрали запись, а файлы остались
(`вне реестра`); обновление выключено, но раздача идёт (`заморожен`).

Важно для демок: собирать их нужно с `base: '/<slug>/'` в vite-конфиге
(или `base: './'`, если внутри нет клиентского роутера), иначе демка
будет искать свои ассеты в `/assets/` портфолио.

### Postgres

Общий Postgres стека (контейнер `pg`), своя роль `aaaver` и своя база
`aaaverdb` — как у соседних проектов. Адрес в `DATABASE_URL`, обязательно
с `sslmode=require`: в `pg_hba` стека стоит `hostssl`. Именно `require`, а
не `verify-full` — сертификат выписан на `db.kiviuly.ru`, а ходим мы по
имени контейнера; трафик машину не покидает.

Таблицы:

- `messages` — все сообщения с формы: текст, IP, user-agent, флаги спама
  (`jsonb`), статус доставки в Telegram;
- `challenges` — выданные pow-задачи (одноразовые, чистятся через час);
- `attempts` — события для rate-limit (чистятся через сутки);
- `settings` — key-value: найденный chat_id, кэш GitHub;
- `schema_migrations` — какие файлы миграций уже применены.

Раз в 10 минут сервер чистит протухшее и пытается дослать в Telegram
сообщения с `delivered = 0` (до 20 попыток на сообщение).

**Схему накатывает сам сервер** на старте: `server/db/migrations/*.sql` по
порядку имён, каждый файл — в одной транзакции вместе с отметкой о себе,
под транзакционной advisory-блокировкой (два процесса не применят одно и
то же дважды). Новая таблица = новый файл `NNN_имя.sql`, существующие не
трогаются.

**База может лежать, сайт — нет.** `depends_on: postgres` этому проекту
недоступен: Postgres описан в родительском `/root/compose.yml`, и ссылка
на чужой сервис из включаемого файла ломает compose. Поэтому сервер
устроен так, чтобы это не имело значения:

- подключение ленивое, миграции идут в фоне с нарастающей паузой;
- статика (портфолио, демки) отдаётся всегда — ей база не нужна;
- всё, что ходит в базу, отвечает `503 db-unavailable`, а не 500:
  недоступное соединение отличается от ошибки запроса по коду
  (`ERR_POSTGRES_SERVER_ERROR` — наш баг, остальное — соединение);
- `/api/health` остаётся 200 и кладёт правду в поле: `{ok, db, dbError}`.
  Healthcheck докера смотрит именно сюда, и перезапускать контейнер
  из-за лежащей базы бессмысленно.

Отсутствие самого `DATABASE_URL` — случай другой: это опечатка в
развёртывании, а не временная неполадка, поэтому в проде процесс падает
сразу (вне прода — предупреждение, чтобы `build` и `preview` работали
без базы).

## Docker

Multi-stage: `deps` (bun install) → `build` (vite build + пререндер) → `runtime`.
В рантайм-образ попадают только `server/`, `scripts/` и `dist/` —
node_modules там не нужен, потому что у сервера нет зависимостей.
Демки (`./sites:/sites`, read-only) монтируются с хоста — они
обновляются без пересборки образа. Базы в образе нет вовсе: она живёт
в общем Postgres стека.

Из этого же образа compose поднимает второй сервис — `sites-updater`
(автодеплой демок). Только у него `sites` смонтирован на запись:
основной сервер физически не может изменить содержимое демок.
Подробности в [deploy.md](deploy.md).
